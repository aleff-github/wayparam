# Packaging & distribution

This page describes how `wayparam` is packaged and how to publish a new release
through the three supported channels: **PyPI**, **Snap Store** and **apt**.

## What is in the repository

| Path | Purpose |
| --- | --- |
| `pyproject.toml` | PEP 621 metadata + `wayparam` console entry point |
| `man/wayparam.1` | manpage, installed by the Debian package |
| `snap/snapcraft.yaml` | Snap recipe (core22, strict confinement, two apps) |
| `debian/` | Debian source package, building **two** binary packages |
| `scripts/build-deb.sh` | local `.deb` / source-package build helper |
| `.github/workflows/release.yml` | publishes all three channels on a `v*` tag |

## Channel 1 — PyPI (already live)

```bash
pipx install wayparam      # or: pip install wayparam
```

The project is on PyPI since 0.3.0 (uploaded manually). The `pypi` job in
`release.yml` only *automates* what is currently a manual `twine upload`, using
**Trusted Publishing** so that no API token has to live in repository secrets.

Because the project already exists on PyPI, configure the publisher from the
project itself — *Manage project → Publishing → Add a new publisher* — not from
the "pending publisher" page (that one is only for names not yet on PyPI). Use:

| Field | Value |
| --- | --- |
| Owner | `aleff-github` |
| Repository | `wayparam` |
| Workflow | `release.yml` |
| Environment | `pypi` |

Until that is done, drop the `pypi` job from `release.yml` and keep uploading by
hand (`python -m build && twine upload dist/*`) — the `snap` and `deb` jobs are
independent and run regardless.

## Channel 2 — Snap

```bash
sudo snap install wayparam
```

One-time setup:

```bash
sudo snap install snapcraft --classic
snapcraft register wayparam          # claim the name (free, first come first served)
snapcraft export-login --snaps wayparam \
  --acls package_access,package_push,package_update,package_release -
```

Store the exported credentials as the `SNAPCRAFT_STORE_CREDENTIALS` repository
secret; `release.yml` then builds and releases to the `stable` channel on tag.

Build and test locally:

```bash
snapcraft                            # produces wayparam_<version>_amd64.snap
sudo snap install --dangerous ./wayparam_*.snap
wayparam --help
```

### The two snap apps

`wayparam` is the CLI; `wayparam.gui` serves the web UI and additionally holds
`network-bind` so it can listen on the loopback interface. A snap is a single
bundle, so the UI cannot be a separate install here the way it is on Debian --
but it adds only tens of KB and never runs unless that command is invoked.

Inside the snap the UI cannot launch the host browser (no desktop interface by
design), so it prints its URL and the user opens it.

### Confinement notes

The snap is **strictly confined**, with `network`, `home` and `removable-media`
plugs. Consequences to keep in mind:

* it can only read/write inside `$HOME` (not hidden dirs) and, after
  `snap connect wayparam:removable-media`, on mounted media — so run it from a
  directory under `$HOME` or point `-o/--outdir` there;
* **do not** set `SSL_CERT_FILE`/`SSL_CERT_DIR` in the recipe. httpx reads those
  variables directly and raises `FileNotFoundError` if they point at a missing
  file, and staging the `ca-certificates` deb does *not* create
  `/etc/ssl/certs/ca-certificates.crt` — that file is generated by
  `update-ca-certificates` in the package postinst, which snapcraft never runs.
  TLS works because httpx depends on `certifi` and uses its bundled
  `cacert.pem`, which the python plugin installs inside the snap;
* `--proxy` to a loopback address (e.g. Burp on `127.0.0.1:8080`) works: the
  `network` plug allows it.

## Channel 3 — apt

There are three routes, in increasing order of effort. They all reuse the same
`debian/` directory.

### The two binary packages

One source package builds both:

| Package | Contents | Depends on |
| --- | --- | --- |
| `wayparam` | CLI, core modules, manpage | `python3-httpx (>= 0.26.0)` |
| `wayparam-gui` | `wayparam-gui` and `wayparam/gui/` only | `wayparam (= ${binary:Version})` |

pybuild would otherwise stage into `debian/python3-wayparam`, a package this
source does not build, which would leave `wayparam` empty -- hence the explicit
`PYBUILD_DESTDIR`. The staged `dist-packages` path is interpreter-versioned at
`dh_install` time, so `debian/rules` locates it rather than hardcoding it, and
dumps the tree under `debian/` when it cannot.

The CI smoke test asserts the split is real: that each package holds its own
executable, and that `index.html` ships with the UI and *not* with the CLI. A
mis-split would otherwise pass unnoticed.

### 3a. `.deb` attached to the GitHub Release (already automated)

```bash
wget https://github.com/aleff-github/wayparam/releases/latest/download/wayparam_0.4.0-1_all.deb
sudo apt install ./wayparam_0.4.0-1_all.deb
# optional, for the web interface:
sudo apt install ./wayparam-gui_0.4.0-1_all.deb
```

No infrastructure needed, but users get no automatic updates.

### 3b. Launchpad PPA (recommended for real `apt install`)

Gives users `sudo add-apt-repository ppa:<user>/wayparam && sudo apt install wayparam`,
with updates through the normal apt upgrade path. Ubuntu only.

1. Create a Launchpad account, upload an OpenPGP key, sign the Ubuntu Code of
   Conduct, and create a PPA named `wayparam`.
2. Set the target series in `debian/changelog` (`noble`, `plucky`, …).
3. Build and upload a **signed source** package:

   ```bash
   ./scripts/build-deb.sh --source
   dput ppa:<your-launchpad-user>/wayparam ../wayparam_0.4.0-1_source.changes
   ```

4. For extra series, rebuild with the series name changed in `debian/changelog`
   (or use `backportpackage`) and bump the revision, e.g. `0.4.0-1~noble1`.

### 3c. Debian / Kali proper

The longest path, but the packaging in `debian/` is already shaped for it:

* **Debian**: file an ITP bug against `wnpp`, then find a sponsor via
  <https://mentors.debian.net>. Run `lintian -EviIL +pedantic` until clean.
* **Kali**: `wayparam` fits Kali's tool scope (passive OSINT). Kali packages
  live at <https://gitlab.com/kalilinux/packages>; the entry point is a "tool
  request" issue on `kali-bugs`, and Kali generally prefers tools that are
  already in Debian or that ship maintainable packaging.

### Dependency caveat

`httpx >= 0.26` is required. Check that the target series ships a new enough
`python3-httpx` before promising support for it:

```bash
rmadison python3-httpx            # Debian
rmadison -u ubuntu python3-httpx  # Ubuntu
```

Older series (e.g. Ubuntu 22.04 jammy, Debian 12 bookworm) ship an older httpx;
either skip those series or relax/verify the lower bound. `pybuild-plugin-pyproject`
is likewise unavailable before bookworm/noble.

## Release checklist

1. Bump the version in `pyproject.toml`, `src/wayparam/__init__.py` and
   `man/wayparam.1`; update `CHANGELOG.md`.
2. `dch -v <version>-1` to add a `debian/changelog` entry (the build script
   refuses to run if the two versions disagree).
3. `ruff check . && pytest -q`.
4. Verify `wayparam --help` and `man ./man/wayparam.1`.
5. Commit, then `git tag -a v<version> -m "v<version>" && git push --tags` —
   `release.yml` does the rest.
